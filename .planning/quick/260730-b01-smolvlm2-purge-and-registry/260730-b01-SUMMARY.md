# Summary — 260730-b01

Chunk (b) of 3. Chunk (a) (dedicated-T4 latency) is merged; chunk (c) is the
report rewrite.

## 1. SmolVLM2 removed

It has no bounding-box grounding head. Prompted for JSON boxes it emitted
**1176 detections across the 94 test images, all labelled `player`**, and scored
0.000 AP on every class — the boxes did not land on the objects. (The old report
said its outputs "did not resolve into detections"; they did, they just missed,
which points at coordinate handling rather than an absent capability. Either way
it was never a clean finding.) It also carried no reproduction target, so it
gated nothing.

Removed: the inferencer, its test, its predictions dump, the manifest row, the
factory registration, and every report reference. Tables regenerated, six VLMs →
five.

### Deliberately not changed

- **`transformers>=4.49.0,<4.52.0`** was pinned with the comment *"SmolVLM2
  requires >=4.49"*, and **`num2words`** was SmolVLM2's processor dependency
  (nothing in this repo imports it). Both **retained and marked unrevalidated**.
  Proving the other four VLMs still load without them requires a GPU re-run of
  the VLM gate, which this change cannot perform. Relaxing them on inference
  would risk a reproduction failure nobody could debug offline.
- **The manifest still accepts a null `expected_map5095`.** SmolVLM2 was its only
  user, so rather than lose the coverage the test now constructs a synthetic
  entry. The capability is kept for adding an exploratory model without gating
  the run.
- The zero-AP fixture moved from SmolVLM2 to **Grounding-DINO**, which has real
  zero-AP classes, so the distinction between a *scored* zero (`0.000`) and an
  *unscored* class (em dash) stays under test.

## 2. Honest caveat added to VLM_VS_FINETUNED.md

Auditing the committed prediction dumps showed **two of the five remaining rows
are not trustworthy as capability measurements**, so the report no longer asserts
them as findings:

- **Grounding-DINO emits 533 detections per image, 99.7% labelled `person`**
  (49,935 / 50,103) and finds the ball **once in 94 images**. `_resolve_label`
  breaks a concatenated multi-phrase label by taking the class name appearing
  earliest in the string; at `text_threshold: 0.01` nearly every token activates,
  so the label spans the whole caption and the tiebreak deterministically returns
  whichever class is listed first in the manifest.
- **Florence-2 ran with `task: "<OD>"`** — the *closed*-vocabulary mode, which
  cannot return custom classes. 923 of 924 detections are `person`. The correct
  token is `<OPEN_VOCABULARY_DETECTION>`.

Prompt effort was also unequal (Gemini hand-tuned, OWLv2 tuned vocabulary, the
other three given a generic COCO list) — the report applies "tuning effort is
itself an unfairness" to the detectors but not yet to the VLMs. Readers are told
to treat Gemini and OWLv2 as the meaningful ceiling until chunk (d) re-runs them.

## 3. Registry corrected

`yolox_m_800.yaml` declared an 800×800 input but recorded the **@640** model's
metrics (0.672 / 0.934; the @800 checkpoint scores 0.723), while the checkpoint
every published YOLOX-M number actually comes from —
`yolox_m_basketball_640.onnx`, pinned by both `reproduction_640.yaml` and
`latency_640.yaml` — had **no card at all**.

Replaced with `yolox_m_640.yaml`: correct 640×640 input, correct 5c *and* 10c
metrics, real sha256 computed from the local artifact
(`5f2f05c6890f513a06e6c94154363b351c1eefde0c57b2c9b16c2d48557d5c77`).

- **`yolox_s_800.yaml` kept.** It is a different checkpoint with no @640
  counterpart; deleting it would drop the model rather than re-point it. Out of
  the scope you approved (which named YOLOX-M).
- **`gcs-manifest.md` left alone.** Its `official-eval-inputs/yolox_m_800/` paths
  are real GCS objects, and it already flags its own mislabelled "YOLOX-M @640
  (reuse)" row as the artifact-selection mix-up the Phase 4 gate exists to catch.
