# Summary — 260801-e01 (chunk e)

Continues 260731-d01, which repaired the Grounding-DINO label collapse and the
Florence-2 task token but could not re-run them. The harness was correct; the
numbers were not. They are now.

## 1. Prompt effort equalised mechanically, not by hand

The report criticised unequal tuning effort and then committed it. Hand-tuning
each model separately would only have moved the advantage to whichever model got
the most attention, so the fix is structural: **every open-weights model is
scored against the same six candidate vocabularies**, and its published prompt is
whichever candidate won *for that model*. The manifest validator rejects a
candidate list that disagrees with the declared budget, so "equal effort" is
checkable by reading the config.

**The search runs on val (96 images), never test.** Choosing a prompt on the
split the report publishes would make the reported number the maximum over six
draws — biased upward and no longer an estimate of zero-shot performance. Both
the schema and the CLI refuse `test`.

Scoring goes through one shared module (`inference/vlm/protocol.score_split`)
rather than a second copy of the pipeline: the remap-before-filter order is
load-bearing, and a search scoring through a different order would rank prompts
against a metric the published run never computes.

## 2. Both starting hypotheses were refuted by measurement

- **Contrastive `referee`/`player` phrasing is catastrophic, not helpful.**
  Grounding-DINO's `player` AP@50 falls 0.828 → 0.000, Florence-2's 0.317 →
  0.000. Longer descriptive phrases produce multi-class labels, which the
  ambiguity guard drops. The mechanism that fixed the old label-collapse bug is
  the same one that makes verbose prompts useless.
- **`rim` cannot be prompted into existence.** Across 5 models × 6 vocabularies
  — 30 measurements — `rim` AP@50 is 0.000 everywhere but one (OWLv2, 0.039).
  The rim collapse is not a vocabulary problem.

**The winner differs by model**, which is what justifies per-model selection:
domain vocabulary for OWLv2 and Grounding-DINO, bare canonical names for
OmDet-Turbo and Florence-2, the generic COCO list for YOLO-World.

## 3. YOLO-World added — and its result verified, not assumed

Added via `ultralytics` in the optional `[vlm]` extra (user-approved licensing
call). `clip-anytorch` is declared explicitly because `set_classes()` otherwise
pip-installs CLIP from a git URL at runtime, silently mutating a locked env.

A 77× `player` drop from adding one word looked like a bug, so it was checked:
with `"basketball player"` YOLO-World emits **zero people across 5 images**;
with `"person"`, 101 — while `basketball hoop` returns an identical box in both.
Class indexing is correct; its CLIP-reparameterised embeddings genuinely go
silent on the compound phrase. Forcing one shared vocabulary for the *look* of
fairness would have published this row at a third of its real score.

## 4. Licences corrected — both were wrong or guessed

- **YOLO-World is GPL-3.0**, not the Apache-2.0 the report published. Verified
  against the upstream `LICENSE`.
- **YOLOE is AGPL-3.0**, built on ultralytics — previously recorded as "likely
  inherits AGPL", a guess. Verified, and **not adopted**: the user's criterion
  was "add it if permissive", and it is not.

## 5. Test-split re-run on CUDA

Ran on a rented vast.ai RTX A4000 (driver 565.57.01), ~$0.11/hr.

`pixi install -e vlm` on Linux produces a **CPU-only torch** — conda-forge
resolves the CPU build unless the GPU variant is requested — which would have
turned a rented GPU into a slow CPU box. Fixed with a new `[feature.vlmcuda]`,
declared-but-not-composed exactly like the existing `[feature.trt]`. Two
non-obvious gotchas are recorded in the config: `pytorch-gpu = "*"` resolves to
pytorch 1.6.0, and pixi needs `system-requirements.cuda` because it does not
detect the `__cuda` virtual package in a container (`CONDA_OVERRIDE_CUDA` does
not work).

Gemini was **not** re-run: billed API, and its harness was never broken. Its row
keeps its existing dump and its hand-tuned prompt, and the report says so.

## 7. The singleton filter was discarding correct detections

Prompting was not the only suspect, and the harness turned out to be at fault
too. `single_best_per_class` kept only the **top-1** ball/rim box per image.
Measured on val: **OWLv2 produces a correct `ball` box in 90.9% of images but
ranks it first in only 51.1%.** The detections existed; we threw them away, and
the result was indistinguishable from a model that could not find the ball.

`k` is now 3, chosen on val across all five open-weights models rather than the
one that motivated the change (mAP@50:95, k=1 → k=3): OWLv2 +0.0107,
Grounding-DINO +0.0002, OmDet-Turbo +0.0002, YOLO-World +0.0006, Florence-2
−0.0004. A floor raised for one model, neutral for the rest — OWLv2 emits a
median of 613 ball candidates per image and had ranking headroom the others lack.

The val estimate held on test (+0.0107 predicted, +0.0132 measured), and it
**breaks the OWLv2 / Grounding-DINO tie** in OWLv2's favour: 0.246 vs 0.234.

The same diagnostic points the other way for `rim`: recall at **any** rank is
0.167, so 83% of images yield no correct rim box at all. Relaxing `k` moves rim
0.001 → 0.012 and no further. The ball was hidden by our filter; the rim is
genuinely not detected. That asymmetry is why both are reported together.

## 8. The COCO `person` alias — investigated, and it is not the culprit

Raised as a review question: does aliasing COCO `person` -> `player` flood the
metric with false positives, given we actually want players and referees?

**Yes on volume, no on cost.** 88% of YOLO-World's `player` boxes (8771 of 9964)
match no ground-truth object. But its true positives have median confidence
0.581 against 0.018 for false positives, and **not one false positive exceeds
0.5** — AP integrates a confidence-ranked curve, so that mass lands where
precision has already collapsed. 68% of them are under half a median GT player's
height: crowd and bench, i.e. real people the dataset does not annotate. A
labelling-convention mismatch, not model error. (Grounding-DINO is the control:
811 of 822 correct, 5 false positives — bought with recall, 817 TPs vs OWLv2's
967.)

**The referee result is real, but the alias does not cause it.** The obvious
story — `person` is a superset that absorbs referees — is wrong. Prompting
YOLO-World with `referee` as the ONLY class returns nothing at all; with
`person` present it returns only people. It cannot ground the word "referee"
under any configuration. `person` is the sole phrase that fires, and the alias
then labels officials `player`. Dropping the alias would lose the players too.

So the row's 0.000 is not "cannot detect referees" — it detects them as people —
but "its only usable vocabulary cannot name them", a concrete limitation of
prompt-then-detect. OmDet-Turbo is the contrast: a working `referee` class
(0.350) and still 262 player-boxes on referees, which IS genuine confusion.

Written up in the report under "Does the COCO `person` alias manufacture false
positives?".

## 9. Two incidents worth recording

- **An orphaned GPU instance.** The session was torn down mid-run on 2026-08-01
  before the instance could be destroyed, and vast.ai's entire domain then went
  NXDOMAIN for ~2 days, so it could be neither reached nor killed. It ran ~41h
  (~$3.20) until the user destroyed it manually. The re-run was subsequently
  restructured as a single detached remote script (`run_all.sh`) with an
  `ALL_DONE` marker, so a dropped session can no longer interrupt or orphan work.
- **A checkpoint footgun.** `Florence2Inferencer`'s default `model_name` is
  `Florence-2-large` while the manifest pins `Florence-2-large-ft`. A diagnostic
  script that omitted the argument silently benchmarked a *different model* and
  produced a misleading number. No committed result was affected — both the
  search and the published run pass the manifest value — but the mismatch is a
  live trap. Incidentally, the base checkpoint scored **+0.029 over `-ft`** on
  val in that accidental run; an untested lead, not a result.
