# Summary — 260730-a01

## Headline

**The report's "latency is not reproducible from this repo" claim was wrong.**
It was neighbour contention on a shared vast.ai T4, not T4-to-T4 hardware
variation. Re-measuring byte-identical ONNX under the *same* TensorRT 10.3.0 on
a sole-tenant GCP T4 with locked clocks recovered the source band.

| Model | shared (old) | dedicated (new) | Δ |
|---|---|---|---|
| YOLOX-M | 14.76 | **5.70** | −61% |
| YOLO26m | 12.99 | **5.85** | −55% |
| DEIM-M | 43.00 | **6.61** | −85% |
| DAMO-YOLO-M | 11.75 | **6.70** | −43% |
| RF-DETR-M | 9.33 | **7.71** | −17% |
| RT-DETRv2-M | 9.55 | **7.93** | −17% |
| RTMDet-M | 17.01 | **8.19** | −52% |

DEIM-M's 43.00 ms was the tell: it landed at 6.61 against the source T4's 6.56.
4 of 7 now sit inside the 4.0–7.1 ms band — a *substantial* reproduction, not an
exact one; the 7.71–8.19 ms trio is unexplained and not hand-waved as noise.
The two in-graph-decode DETRs moved least (−17%), consistent with contention
penalising multi-kernel dense-head/NMS paths hardest.

## Consequence for the leaderboard (feeds chunk c)

The speed ranking **reordered**, and it inverts a conclusion drawn from the old
data. YOLOX-M is now the fastest model measured (5.70 ms), ahead of YOLO26m
(5.85). RF-DETR-M fell from 1st to 5th.

Recomputed Pareto frontier (nothing both faster and more accurate):
- **Overall:** YOLOX-M (5.70, 0.672) and YOLO26m (5.85, 0.716)
- **Apache-2.0 only:** YOLOX-M (5.70, 0.672) and DEIM-M (6.61, 0.686)

## Method

GCP `n1-standard-8` + 1×T4, us-central1-a, sole tenant, persistence mode on, SM
clock locked to 1590 MHz. TensorRT pinned to **10.3.0** via
`nvcr.io/nvidia/tensorrt:24.08-py3` — deliberately the same version as the
discredited run, so tenancy was the only changed variable. All 7 ONNX staged
from GCS after md5-verification against the locally pinned artifacts.
EfficientNMS grafts for YOLOX/DAMO/RTMDet were built during the run (none
existed in the repo). Cost ~$1.60; VM deleted.

Raw results also archived at
`gs://deep-ego-model-training/ego-training-data/basketball-data/eval/latency-dedicated-t4-2026-07-30/`.

## Repo defects found and fixed

1. **`resolve_trt_version()` misattributed provenance** — preferred the
   `tensorrt` Python binding over the `--trtexec` binary doing the work. The run
   made it concrete: binding 10.16.1.11 vs builder 10.3.0. Its fallback regex
   also returned the NGC *container tag* `24.08`.
2. **`pip` missing from `[feature.trt]`** — the documented setup command
   `pixi run -e trt pip install -e . --no-deps` fails with `pip: command not found`.
3. **`trtexec` absent from the `trt` env entirely** — the `tensorrt` wheel ships
   only the Python binding, so **the documented LAT-02 workflow could not run as
   published**. Now documented as requiring an external `trtexec`.

Defects 2 and 3 together mean nobody could have re-run LAT-02 from the repo as
specified; that is also why the committed results (10.3.0) and the pixi pin
(`tensorrt >=10.16,<11`) were never reconcilable.

## Known gap

**RTMDet-M's on-GPU NMS delta is unavailable.** Its ungrafted graph cannot build
under TensorRT (mmdeploy `end2end` export, pre-NMS `TopK` with K > 3840). This is
expected — it is why `graft_efficientnms.py` strips that tail — reproduced
identically on both machines, and affects only the `to_boxes − model_only`
difference. Its to-boxes number is valid.
